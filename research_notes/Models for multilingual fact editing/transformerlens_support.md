### Takeaway

### Inferences
- SmolLM2 is `LlamaForCausalLM`, and `convert_hf_model_config` has a generic `architecture == "LlamaForCausalLM"` branch (L780-808, reads sizes from the HF config, handles llama3 rope scaling). So appending the SmolLM2 name to `OFFICIAL_MODEL_NAMES` at runtime might make HookedTransformer load it, but the name check is the only barrier and "llama" is not in the name, so it would go through `AutoConfig` (hub). This is a monkeypatch, UNVERIFIED by execution; I would not rely on it without a logit-parity check against HF.
- Phi-4-mini through the HookedTransformer `Phi3ForCausalLM` branch would be wrong even if the name were registered: that branch sets `rotary_dim = hidden_size // num_attention_heads` (=128) while Phi-4-mini config has `partial_rotary_factor: 0.75` (rotary 96), `sliding_window: 262144` and longrope scaling that the branch does not model. Use the Bridge for Phi-4-mini, Granite, SmolLM2, Aya.
- For the project's existing pattern, Gemma-2/3 and Llama need no network; Qwen2.5/Qwen3/Phi-3/BLOOM need either network or a cached config.

## Q2. Architecture quirks that affect this project's causal tracing / ROME code, and which hook names exist

### Takeaway
All candidate decoder models expose `hook_embed`, `blocks.{l}.hook_resid_post`, `blocks.{l}.hook_mlp_out`, `blocks.{l}.mlp.hook_post`, and `ln_final.hook_normalized` in HookedTransformer (with `from_pretrained_no_processing`). Three quirks need code changes: (a) Gemma-2 needs the final-logit soft-cap applied in the project's hand-rolled `last_logits_grad`; (b) in Gemma-2/3 `hook_mlp_out` is AFTER the post-feedforward RMSNorm, so a rank-1 update to `W_out` does not add the edited vector directly; (c) BLOOM uses LayerNorm (has bias `b`), non-gated MLP and ALiBi, so `ln_final.w`-only logic is wrong for it.

### Inferences
- ROME on Gemma-2/3: ROME's rank-1 update sets `W_out' k = W_out k + delta`-style so that the MLP output equals a target v*. In Gemma-2/3 the quantity the project optimises (`hook_mlp_out` + delta) lies after a nonlinear RMSNorm (`ln2_post`) of the raw `W_out @ hook_post`; a rank-1 change to `W_out` therefore changes the pre-norm vector and the normalised result is rescaled. The project's `apply_edit` (which treats `delta` as the additive change to the raw `W_out k` output) is not directly valid. Options: optimise delta on the pre-norm vector via a hook on `ln2_post.hook_normalized` (then convert: the pre-norm target is `scale_orig * normalised_target`), or compute `v*` from `ln2_post.hook_scale`. This is my derivation from the code, not something I found documented, and I did not test it. Llama/Qwen/Phi-3/BLOOM have no post-norm so the existing logic holds.
- The project's `last_logits_grad` also computes `(h * ln_final.w) @ W_U` with no bias term and no soft-cap, so it is exact for Llama/Qwen2.5/Qwen3/Phi-3/Gemma-3, needs `30*tanh(x/30)` for Gemma-2, and needs `+ ln_final.b` plus mean-centering of the normalised input for BLOOM (`LayerNorm`; `hook_normalized` there is after centering/scale but before `w`,`b`; I did not read `layer_norm.py`, UNVERIFIED).
- Causal tracing noise: `pooled_embedding_std` uses `model.W_E`; for Gemma that is the pre-scaled embedding (x sqrt(d_model); for gemma-2-2b sqrt(2304) = 48, exactly representable in bf16), so noise magnitudes are consistent with what `hook_embed` sees. Fine as is.
- bf16 numerics for Gemma: TL stores `(1 + w)` in an `nn.Parameter` of dtype `cfg.dtype` (bf16; `RMSNorm.w = nn.Parameter(torch.ones(length, dtype=cfg.dtype))`, `load_state_dict` copies into it), whereas HF keeps `w` in bf16 and computes `1 + w.float()`. For weights where `1+w` is near 1, bf16 has 2^-7 relative spacing, so TL's Gemma norms are slightly quantised relative to HF. Expect small logit differences vs HF; verify with a parity check.
- Because `n_ctx` for Qwen2.5 is 32768 and the rotary cache is `min(n_ctx, ROTARY_INITIAL_CACHE_SIZE)` while the causal mask is built per forward (L100-150), memory cost of large `n_ctx` is small, but passing `n_ctx=2048` is still harmless (TL only warns when `n_ctx` exceeds the default).
- Qwen3 `trust_remote_code=True` is forced by TL; with `transformers` 5.19 Qwen3 is a native class, so I would expect no remote code to be fetched, but this is UNVERIFIED.

### Inferences
- Models that plausibly fit forward+backward at ~7.9 GiB with the project's re-layout trick and short prompts (batch 1, few tokens): Qwen2.5-0.5B/1.5B/3B, Qwen3-0.6B/1.7B, Gemma-3-1B, Llama-3.2-1B, Gemma-2-2B, bloom-1b1/1b7. Qwen2.5-3B (1.6 GiB headroom) and Gemma-2-2B (~2 GiB headroom) are comparable to the already-working Llama-3.2-3B (~1.2 GiB headroom). bloom-3b and Phi-3-mini-4k are marginal (headroom ~1.2 and ~0.8 GiB, and activations/KV/attention-pattern memory with the Windows desktop's ~0.5 GiB display use may break them). Qwen3-4B and Gemma-3-4B exceed the card in TL bf16 (even HF-tied Gemma-3-4B is 7.23 GiB before any activations).
- Memory saving for tied models: replacing `model.unembed.W_U` with a Parameter that is a transposed view of `model.embed.W_E` (`W_E.T`) would remove the duplicate embedding for Llama/Qwen (saves 0.25-0.73 GiB; for Qwen3-4B this gives ~7.5 GiB, still too big). It does NOT work for Gemma because TL's `W_E` is pre-scaled by sqrt(d_model) while `W_U` is not. `Unembed.forward` does `W_U.T.contiguous()`, which for `W_U = W_E.T` is `W_E` itself (already contiguous), so no copy. Untested.
- The "max" copy columns are an upper bound (all layers' copies retained for backward), e.g. Llama-3B would be ~5.3 GiB (3.94 MLP + 1.31 attn) vs the 1.2 GiB the project observed; the observed number is lower, likely because gradients flow only from the edit layer upward and `torch.no_grad`/hook paths skip the earlier layers, but I did not measure this. Without re-layout, Qwen2.5-3B (4.54 + 0.63 GiB) and Gemma-2-2B (3.08 + 0.69) would behave similarly to Llama-3B; with re-layout those copies disappear.
- Gemma-2 attention is eager with soft-cap, so attention pattern memory is O(heads x q x k) per layer; with prompts of <100 tokens this is negligible. The 256k vocab matters only for weights (W_E 1.10 GiB + W_U 1.10 GiB for gemma-2-2b).
- `share_transposed_mlp_weights` as written would fail for MHA models (Phi-3-mini, BLOOM) because it hard-codes `_W_K/_W_V`, and for BLOOM because of `W_gate`; it also hard-codes the `W_O` layout. Per-family branching is needed.

### Gaps
- No measured VRAM for any candidate (no model was loaded; the constraint was not to download weights). All figures are arithmetic plus the project's one measured data point (Llama-3.2-3B, ~1.2 GiB per pass).
- Activation memory for backward (hooks keep `act.clone()`, QK-norm and Gemma post-norm extra activations) was not estimated; QK-norm (Qwen3, Gemma-3) and post-norms (Gemma) add a few tensors per layer.
- Windows display driver overhead (~553 MiB used at idle) reduces the usable ~7.4 GiB; exact usable budget not measured.
